# My Engineering Story — Built by Transition

My career has not been a straight line through one technology stack.

It has been a sequence of transitions.

The technologies changed. The domains changed. The scale changed.

The recurring pattern did not:

~~~text
Unknown
  ↓
Research
  ↓
Understand
  ↓
Build
  ↓
Lead
  ↓
Improve
~~~

This document keeps the detailed chronology behind the shorter story shown on my GitHub profile.

---

# Act I — I didn't start in software

## Mechatronics: making a whole system work

I studied **Mechatronics**.

My graduation project was an **automatic rice weighing and packaging conveyor system** combining mechanical components, sensors, C#, Android, and a C# monitoring application.

Much of the work was self-directed.

I had to understand how devices communicated, how state could be monitored, how software controlled physical behavior, and how several components became one working system.

That became the first version of my engineering method:

> When the system is unfamiliar, understand the pieces, understand how they connect, then make the whole thing work.

---

# Act II — I kept entering systems I didn't know

## End of 2017: COBOL fresher → Java engineer

At the end of 2017, I started professionally as a **COBOL fresher**.

I was still new to professional software engineering and had only recently begun learning SQL.

After COBOL training, the project direction changed.

I moved into:

~~~text
AngularJS
Java 6 / Java 8
SQL
Enterprise applications
~~~

I had to learn quickly: frontend/backend integration, database usage, existing codebases, and professional delivery practices.

I performed well and continued on the Java path.

## Migration became my classroom

For roughly the next three years, modernization and migration became a major part of my work.

~~~text
Java 6 → Java 8
Adobe Flex → Angular
Angular → Angular 13
~~~

Migration showed me that a legacy system is more than its framework.

It contains business behavior, hidden dependencies, technical debt, operational assumptions, performance characteristics, undocumented rules, and years of accumulated decisions.

I gradually stopped asking only:

> How do I implement this?

and started asking:

> Why does the system behave this way?

---

# Act III — The problem became bigger than code

My work expanded into Shell, Bash, automated deployment, batch deployment, JMeter, performance testing, and supporting engineering tools.

The questions became broader:

~~~text
What happens under load?
Where is the bottleneck?
How does deployment fail?
What can be automated?
What evidence proves the system is healthy?
~~~

This was an early step from application development toward systems thinking.

Later, on a **Japanese securities platform**, performance became an end-to-end problem involving:

~~~text
Frontend
  ↓
API
  ↓
Business logic
  ↓
Database
  ↓
Data model
~~~

I worked on backend performance, database optimization, high-volume data processing, chart-data optimization, API responsiveness, and frontend performance.

A slow chart is not necessarily a frontend problem.

A slow API is not necessarily a backend problem.

The real problem may exist elsewhere in the system.

---

# Act IV — Responsibility became bigger than myself

## First leadership responsibilities

I became a leader for an internal **contract-management system**.

My responsibility expanded from personal implementation to team tasks, progress, technical issues, integration, deployment, quality, and helping engineers move forward.

A good engineer can solve a difficult technical problem.

A leader has to create the conditions for a team to solve problems reliably.

## Leaving the familiar stack: Mendix

After years of Java and Angular, I stepped into **Mendix low-code**.

Again, I was outside my comfort zone.

I learned the platform and eventually earned the **Mendix Advanced Developer certification**.

The most valuable part was taking it into production.

## Building with a Japanese startup

I led a team building a warehouse-rental management product for a **Japanese startup**.

I communicated directly with the customer and Product Owner and worked on requirement clarification, solution design, estimation, technical decisions, prioritization, and business/engineering trade-offs.

The product did not achieve the success we hoped for.

That taught me:

> A system can be technically well built and still fail as a product.

Engineering quality matters, but product success also depends on market, timing, business model, customer behavior, and many other factors.

## A new market and another modernization challenge

I later moved into projects for the **Korean market**.

One major challenge was:

~~~text
Struts
  ↓
Spring
~~~

There was no perfect roadmap waiting for me.

I investigated architecture, dependencies, framework behavior, compatibility, migration options, and technical risks, then turned that investigation into a practical solution and implementation path.

By this point, I had become comfortable with not knowing the answer at the beginning.

## When the browser became the platform

I then led a **Chrome Extension** project performing real-time actions directly on web pages.

The technical domain was different: DOM behavior, browser lifecycle, asynchronous events, extension/web-page communication, real-time actions, compatibility, and state synchronization.

Technology unfamiliarity itself was no longer the main risk.

The real question was whether I could investigate fast enough, form a correct model, validate the solution, and guide implementation.

## Technical Leader at scale

My next major step was Technical Leader for a **Spring Boot + React security platform** with roughly **40 people**.

At that scale, technical leadership meant architecture, technical direction, cross-team dependencies, standards, integration, deployment, production issues, performance, security, and risk.

The question changed from:

> How should I implement this feature?

to:

> How should multiple teams build this system together?

My work then expanded across several smaller teams and parallel workstreams.

Responsibilities increasingly included:

~~~text
Technical investigation
Architecture
Solution design
Estimation
Bidding
Planning
Technical review
Risk analysis
Team support
~~~

I still code when needed, but code is no longer the only important output.

A strong technical decision can enable many correct implementation decisions downstream.

# Act V — Search helped me learn. AI changed the interface.

## Before AI, search was my research partner

For most of my career, when I entered a domain I did not understand, my first move was **search**.

~~~text
Problem
  ↓
Google Search
  ↓
Documentation / examples / articles
  ↓
Compare approaches
  ↓
Prototype
  ↓
Understand
  ↓
Implement
~~~

This is how I learned frameworks, investigated strange behavior, explored migration options, diagnosed performance issues, and entered unfamiliar domains.

It worked, but it was fragmented.

I had to collect the pieces and build the mental model myself.

## AI did not replace research

Generative AI changed the speed and shape of that workflow.

Instead of only searching for documents, I can now work interactively with systems that help me:

- explain unfamiliar concepts
- compare alternatives
- summarize documentation
- challenge assumptions
- explore architecture
- review code
- create tests
- investigate repositories
- propose implementations
- critique solutions

Previously:

~~~text
Search
  ↓
Read
  ↓
Collect fragments
  ↓
Build understanding
  ↓
Work
~~~

Now:

~~~text
Ask
  ↓
Explore
  ↓
Challenge
  ↓
Understand faster
  ↓
Work together
  ↓
Review together
~~~

**Search helped me find information.  
AI helps me turn information into understanding, work, and review.**

## The AI tools in my daily workflow

I do not treat one model as the answer to everything.

**Microsoft Copilot** helps with productivity, synthesis, drafting, and business-context work.

**GitHub Copilot** sits close to implementation: coding, refactoring, tests, and repository exploration.

**Claude** is useful for long-context analysis, architecture reasoning, codebase understanding, alternative approaches, and technical discussion.

**ChatGPT** spans research, planning, architecture, solution exploration, technical review, documentation, and decision support.

More recently, I have been using **Codex** increasingly for repo-native engineering work:

~~~text
Inspect repository
  ↓
Understand context
  ↓
Create a plan
  ↓
Modify code
  ↓
Run tests
  ↓
Review changes
  ↓
Work through GitHub
~~~

AI is no longer only helping me think about the work.

It can increasingly participate in doing the work.

# Act VI — The tools changed. The pattern didn't.

The important question is becoming less:

> Which AI tool is best?

and more:

> Which engineering role should AI perform here?

I increasingly think in roles such as:

~~~text
Research
Architecture
Coding
Testing
Review
Migration
Risk
~~~

Different tools can fill different positions.

The engineering system around them matters more than the brand of model.

Before:

~~~text
Unknown
  ↓
Research
  ↓
Understand
  ↓
Build
  ↓
Review
  ↓
Lead
~~~

Now:

~~~text
Unknown
  ↓
AI-assisted Research
  ↓
Faster Understanding
  ↓
AI-assisted Execution
  ↓
Independent Review
  ↓
Evidence
  ↓
Human Decision
  ↓
Lead at a larger scale
~~~

AI helps me understand faster, research faster, implement faster, review more thoroughly, and explore more alternatives.

But speed is not correctness.

Human responsibility remains essential for context, intent, architecture, constraints, trade-offs, risk, validation, and final decisions.

My preferred model is:

~~~text
AI execution
      +
Engineering evidence
      +
Independent review
      +
Human decision
~~~

This is why I am increasingly interested in **AI-assisted engineering governance**.

The question I am exploring now is:

> How should humans and AI build software together reliably?

---

# The next transition

I do not know which framework will dominate engineering ten years from now.

I do not know which AI model will dominate either.

The durable capability is being able to enter an unfamiliar system, form a useful understanding, find the real problem, design a path forward, choose the right tools, and lead execution.

That is what I have been doing since the rice-conveyor project.

AI now amplifies that process.

**The tools changed. The scale changed. The pattern didn't.**
