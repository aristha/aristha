## Engineering Journey

### Mechatronics → Software

My graduation project was an **automatic rice weighing and packaging conveyor system**.

I combined hardware, sensors, C#, Android, and a C# monitoring application. Much of it was self-taught: how to connect components, observe state, control devices, and make the whole system work together.

### 2017 → COBOL → Java

I started my first job at the end of 2017 as a **COBOL fresher** and was only beginning to learn SQL.

After training, my project direction changed to AngularJS, Java 6/8, SQL, and enterprise applications. I had to learn a new stack quickly, performed well, and continued on the Java path.

### Legacy Modernization Became My Classroom

Over the following years, I worked on modernization such as:

~~~text
Java 6 → Java 8
Adobe Flex → Angular → Angular 13
Struts → Spring
~~~

I also worked with Shell, Bash, deployment automation, batch deployment, JMeter, and performance testing.

Migration taught me to understand **behavior, dependencies, data, performance, operational constraints, and hidden business rules**, not just frameworks.

### Developer → Leader → Technical Leader

I first led an internal contract-management system.

I then stepped outside Java into **Mendix**, earned the **Advanced Developer certification**, and led a production project for a Japanese startup building a warehouse-rental management product.

That role included direct communication with the customer and Product Owner, solution design, estimation, requirement clarification, and business/engineering trade-offs.

The product did not achieve the outcome we hoped for, but it taught me an important lesson:

> Good engineering is necessary, but it is not sufficient for product success.

I later returned to Java and Angular as a leader on a **Japanese securities platform**, focusing on backend performance, database optimization, large data processing, chart-data optimization, and end-to-end responsiveness.

In the Korean market, I investigated and implemented a **Struts-to-Spring migration**, led a **Chrome Extension** project performing real-time actions on web pages, and then became Technical Leader for a **Spring Boot + React security platform** with a team of roughly 40 people.

Today I support multiple teams and workstreams, with responsibilities increasingly centered on:

## From Google Search to AI Engineering

Earlier in my career, when I met an unfamiliar technology or problem, my default engineering tool was **Google Search**.

The workflow was:

~~~text
Problem
  ↓
Search
  ↓
Read documentation and examples
  ↓
Compare approaches
  ↓
Prototype
  ↓
Understand
  ↓
Implement
~~~

That habit has not disappeared.

What changed is the interface.

Today, AI increasingly acts like a set of engineering collaborators that help me:

- understand unfamiliar systems faster
- research and compare alternatives
- explore solutions
- implement work
- review my reasoning
- review code
- generate tests
- challenge assumptions
- summarize evidence

### My Daily AI Toolchain

- **Microsoft Copilot** — productivity, synthesis, and business-context work
- **GitHub Copilot** — coding, refactoring, tests, and repository exploration
- **Claude** — long-context analysis, architecture reasoning, and alternative solutions
- **ChatGPT** — research, planning, architecture, technical review, and decision support
- **Codex** — increasingly for repo-native execution: inspect, plan, modify, test, review, and work through GitHub

The important shift is not from one search tool to one AI tool.

It is from:

~~~text
Search → Read → Understand → Do everything myself
~~~

toward:

~~~text
Problem
   ↓
AI-assisted research
   ↓
Solution exploration
   ↓
Implementation
   ↓
Independent review
   ↓
Evidence
   ↓
Human decision
~~~

AI helps me **understand faster, work faster, and review more thoroughly** — while technical responsibility remains human.
